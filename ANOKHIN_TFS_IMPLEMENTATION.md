## 2. Что было ДО (реактивная архитектура, близкая к OODA)

### Старый пайплайн:

```python
# stages.py — до ТФС
def run_full_pipeline(t, values, domain="finance"):
    # Screen → Fit → Score → Done
    screening = run_screening(t, values, domain)
    fit = run_structural_fit(t, log_price, domain)
    return PipelineResult(screening, fit, verdict, confidence)
```

**Проблемы:**
1. ❌ **Нет предсказания ДО действия** — система не знает, что ожидает увидеть
2. ❌ **Нет критерия "достаточно хорошо"** — всегда идёт до конца, даже если результат очевидно плох
3. ❌ **Multi-window fallback = полный перезапуск** — не целенаправленная коррекция
4. ❌ **Нет мотивации** — pipeline не знает "зачем" он фитит и стоит ли тратить ресурсы

**Это было близко к OODA Loop:**
- Observe (screening) → Orient (domain context) → Decide (fit) → Act (verdict)
- ❌ Непредсказывающая, реактивная модель
- ❌ При ошибке — полный перезапуск на другом окне

## 3. Что стало ПОСЛЕ (предвосхищающая архитектура ТФС)

### Новый пайплайн с Акцептором:

```python
# acceptor.py — ТФС архитектура
def run_tfs_pipeline_iteration(t, values, domain, max_iterations=3):
    # 1. Афферентный синтез: domain + HMM + historical → context
    # 2. Акцептор: ПРЕДСКАЗАТЬ ожидаемые параметры ДО фита
    # 3. Программа действия: LPPLS fit
    # 4. Обратная афферентация: сравнить с акцептором
    # 5. Решение: accept / targeted retry / reject
```

**Ключевые улучшения:**

| Аспект | Было (OODA-style) | Стало (ТФС) | Выигрыш |
|--------|-------------------|-------------|---------|
| **Предсказание** | ❌ Нет | ✅ До фита знаем ожидаемые m, ω, tc | Знаем что искать |
| **Критерий завершения** | ❌ Всегда до конца | ✅ satisfaction_score > 0.8 → done | Экономия ресурсов |
| **Retry при ошибке** | ❌ Полный перезапуск | ✅ Корректируем конкретный параметр | Быстрее сходимость |
| **Мотивация** | ❌ Нет | ✅ HMM prob = "потребность" | Адаптивные ресурсы |

## 4. Детальная реализация

### 4.1 Акцептор результата действия

**Что делает:** Предсказывает ожидаемые параметры LPPLS ДО того как запустить оптимизацию.

```python
acceptor = create_acceptor(
    domain="finance",
    t=t,
    values=values,
    hmm_bubble_prob=0.6,
    historical_params=[...]  # Байесовское обновление
)

# Результат:
#   m_expected: (0.3, 0.6)      # Ожидаемый диапазон m
#   omega_expected: (7.0, 10.0)  # Ожидаемый диапазон ω
#   min_r_squared: 0.85          # Минимальный R²
#   confidence: 0.7              # Уверенность в предсказании
```

**Источники предсказания:**
1. **Domain priors** — характерные диапазоны для домена (finance vs commodities vs housing)
2. **HMM bubble probability** — высокая вероятность → ожидаем сильный сигнал (уже диапазоны)
3. **Historical fits** — байесовское обновление на основе прошлых фитов
4. **Data characteristics** — много данных → ожидаем хороший фит

**Аналогия с биологией:** Это как дыхательный центр мозга, который "знает" ожидаемый уровень CO2 в крови — если реальное значение совпадает, дыхание нормальное; если нет — корректирует.

### 4.2 Обратная афферентация (Comparator)

**Что делает:** Сравнивает реальные параметры фита с предсказанными акцептором.

```python
comparison = compare_with_acceptor(
    acceptor=acceptor,
    actual_m=0.45,
    actual_omega=8.5,
    actual_r_squared=0.92,
    ...
)

# Результат:
#   acceptor_match: True           # Совпало!
#   mismatches: []                 # Нет расхождений
#   satisfaction_score: 1.0        # Полное удовлетворение
#   retry_needed: False            # Не нужен retry
```

**Если есть расхождения:**
```python
#   mismatches: ["m=0.15 outside expected [0.30, 0.60]"]
#   retry_needed: True
#   retry_action: "widen_m_range_lower"  # Целенаправленное действие!
```

### 4.3 Целенаправленный Retry

**Ключевое отличие от OODA:** retry не "начни сначала", а "исправь конкретную проблему".

| Расхождение | Retry Action | Что делает |
|-------------|--------------|------------|
| `m` слишком низкий | `widen_m_range_lower` | Расширяет нижнюю границу m (0.1 → 0.05) |
| `m` слишком высокий | `widen_m_range_upper` | Расширяет верхнюю границу m (0.9 → 1.0) |
| `ω` слишком высокий | `widen_omega_range_upper` | Расширяет верхнюю границу ω (13 → 15) |
| R² чуть ниже порога | `relax_r2_threshold` | Снижает порог R² на 0.05 |
| R² сильно низкий | `reject_poor_fit` | Отказ от фита (нет смысла retry) |
| `ω` слишком низкий | `reject_likely_not_bubble` | Отказ (малая частота ≠ пузырь) |

**Это принципиально отличается от OODA**, где несоответствие ведёт к новому Observe (полный перезапуск без адресной коррекции).

### 4.4 Встроенный критерий завершения

**ТФС система ЗНАЕТ когда остановиться:**

```python
if comparison.acceptor_match or comparison.satisfaction_score > 0.8:
    # СОВПАДЕНИЕ с акцептором → ЗАВЕРШЕНИЕ
    return result  # Done!

if not comparison.retry_needed or iteration == max_iterations:
    break  # Нет смысла продолжать
```

**Сравнение с OODA:**
- OODA: петля продолжается непрерывно, остановка задаётся извне
- ТФС: система сама знает "достаточно хорошо" → внутреннее завершение

## 6. Практическая ценность для PhaseBreak

### 6.1 Что реально улучшится

**1. Раннее отклонение плохих фитов**
```python
# ДО: fit → check → reject (потратили время на фит)
# ПОСЛЕ: predict → fit → compare → reject (знаем заранее что будет плохо)
```
Если акцептор предсказывает слабый сигнал (low confidence), можно **пропустить фит вообще** или использовать **облегчённый фит** (меньше grid points, меньше bootstrap).

**2. Адаптивное выделение ресурсов**
```python
# Акцептор знает "мотивацию" через HMM bubble probability
if hmm_bubble_prob > 0.7:
    # Высокая мотивация → полный фит (grid=12, bootstrap=100)
    use_full_pipeline()
elif hmm_bubble_prob < 0.3:
    # Низкая мотивация → лёгкий скрининг (grid=6, bootstrap=10)
    use_quick_scan()
```

**3. Объяснимость решений**
```python
# ДО: verdict = "NO_BUBBLE" (почему? непонятно)
# ПОСЛЕ: verdict = "NO_BUBBLE" потому что:
#   - m=0.15 вне ожидаемого диапазона [0.30, 0.60]
#   - R²=0.65 ниже ожидаемого 0.85
#   - satisfaction=0.2 (очень низко)
#   → 2 targeted retry attempts failed → reject
```

### 6.2 Что НЕ изменится

- **Точность детекции** — ТФС не меняет математику LPPLS, только процесс принятия решений
- **Бенчмарк-результаты** — те же 76% precision, 61% recall (фильтры те же)
- **tc точность** — те же ±4 дня (оптимизатор тот же)

**ТФС улучшает ПРОЦЕСС, не результат.**

## 8. Вызовы и Trade-offs (из анализа + наши)

### 8.1 Стоимость акцептора

**Проблема:** Создание акцептора требует дополнительных вычислений (domain analysis, historical lookup).

**Решение:** Акцептор лёгкий (~1ms) по сравнению с LPPLS фитом (~100ms-5s). Overhead < 1%.

### 8.2 Определение "достаточного результата"

**Проблема:** Как формализовать критерий завершения для LPPLS?

**Решение:** satisfaction_score на основе:
- Совпадение параметров с акцептором (40%)
- R² качество (30%)
- Quality score (20%)
- HMM согласие (10%)

### 8.3 Самооценка без внешней верификации

**Проблема из анализа:** "Self-correction without external verification is fundamentally unreliable."

**Решение в PhaseBreak:**
- Comparator использует **детерминированные правила** (Sornette filters), не LLM-оценку
- Исторические данные = **внешняя верификация** (реальные пузыри прошлого)
- Бенчмарк 58 эпизодов = **ground truth** для калибровки акцептора

## 12. Выводы

### Что реально даёт архитектура ТФС:

1. ✅ **Предвосхищение результата** — система знает что искать ДО фита
2. ✅ **Встроенный критерий завершения** — знает когда "достаточно хорошо"
3. ✅ **Целенаправленная коррекция** — retry исправляет конкретную проблему
4. ✅ **Мотивационный контекст** — HMM prob как "потребность" системы
5. ✅ **Полная объяснимость** — знаем ПОЧЕМУ приняли/отклонили результат

### Чего ТФС НЕ даёт:

- ❌ Не улучшает точность детекции (те же 76% precision)
- ❌ Не заменяет LPPLS математику (оптимизатор тот же)
- ❌ Не решает проблему малых выборок (n=58)

### Главный инсайт:

> **ТФС меняет природу коррекции: от слепого повтора к целенаправленному исправлению конкретного расхождения.**

Это и есть то, чем биологически-адаптивные системы Анохина отличаются от простых кибернетических петель обратной связи.
